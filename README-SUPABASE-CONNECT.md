# Подключение кошелька, продавцов и админки к Supabase

Пока `supabase-config.js` содержит `YOUR_PROJECT`, сайт работает в **демо-режиме** (localStorage, как раньше).
Как только в конфиге настоящие URL и anon-ключ — **всё идёт через Supabase**: вход, кошелёк, заявки, объявления, админка.

## 1. SQL (в таком порядке, SQL Editor)
1. `supabase-schema.sql` — уже выполнен.
2. `wallet-marketplace-migration.sql` — уже выполнен.
3. **`wallet-frontend-support.sql` — новый, обязателен.** Идемпотентный. Что делает:
   - **закрывает дыру модерации:** без него продавец мог сам поставить своему объявлению `status='active'` и обойти проверку;
   - статус «Проверка» по кнопке «Я оплатил(а)»;
   - блокировка пользователя (заодно ставит его объявления на паузу и запрещает денежные заявки);
   - Storage-бакет `listing-images` для обложек (каждый продавец пишет только в свою папку).

## 2. Конфиг
Скопируйте `supabase-config.example.js` в `supabase-config.js` и впишите Project URL и **anon/publishable** ключ (никогда не `service_role`).
В Supabase: Authentication → Providers → Email → **выключить Confirm email** (вход идёт по логину через служебный email).

## 3. Администратор
Обычный `UPDATE profiles SET role='admin'` из SQL Editor блокируется триггером `protect_profile_privileges`. Безопасный способ:
```sql
alter table public.profiles disable trigger protect_profile_privileges_trigger;
update public.profiles set role='admin' where username='Kolobok';
alter table public.profiles enable trigger protect_profile_privileges_trigger;
```
Вход в админку теперь проверяется **на сервере** (`profiles.role='admin'`), жёсткий пароль в браузере в этом режиме не используется.

## 4. Реквизиты для пополнения
Админка → Настройки → «Реквизиты для пополнения» (хранятся в `wallet_payment_settings`, видны только авторизованным через `get_deposit_instructions()`).

## Что уже работает через Supabase
Регистрация/вход/выход · баланс · пополнение (код из 5 цифр, подтверждение только админом) · вывод на карту и USDT TRC20 (резерв суммы атомарно) · история операций · заявка продавца · панель продавца (создать/редактировать/снять с продажи/вернуть на проверку, обложка в Storage) · каталог только из одобренных объявлений · админка: пополнения, выводы, модерация, продавцы, пользователи + блокировка, балансы и история операций, реквизиты.

## Что пока НЕ подключено (осознанно)
- **Покупка товара с баланса.** Таблицы `orders`/`favorites` ссылаются на старую `products`, а объявления лежат в `seller_listings`; нужна отдельная SQL-функция покупки (списание, комиссия, зачисление продавцу, запись в ledger). Кнопка «Купить» честно сообщает об этом и не создаёт фальшивых заказов.
- Избранное, заказы и жалобы в админке остаются локальными (localStorage).
- Удаление аккаунтов из панели (нужен service_role) — вместо него блокировка.

## Тесты
`tests/` — сквозной тест на настоящем Postgres (нужны Postgres 16, Node и Playwright): интерфейс → подмена supabase-js → реальные схема, RLS, триггеры и RPC.


## Исправление заявок продавцов и объявлений от KLB STORE

Примените `seller-applications-store-admin-fix.sql` после основных миграций. В предоставленной SQL-схеме заявка продавца использует поля `username` и `benefits`; фронтенд обновлён под эти названия. Администратор может открыть профиль на витрине → «Объявления KLB STORE» и создавать товары от имени магазина. Для этих записей `seller_id` остаётся UUID администратора, а в каталоге продавец отображается как `KLB STORE`. Новые объявления всё равно проходят модерацию. Скрипт также делает одобрение/отзыв статуса продавца совместимым с вариантами схемы, где базовая роль называется `buyer` или `user`.
